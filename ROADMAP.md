Excellent points. Moving **Guardrails** into the local registry makes the system truly modular—allowing you to swap out safety protocols as easily as you swap out tools. Using **ChromaDB** for Phase 2 gives your Orchestrator a robust "long-term memory" to handle semantic routing.

Here is the updated roadmap for your local V1.

---

## Phase 1: The Pluggable Registry
The goal here is to treat every component as a "Lego brick." By placing Guardrails in the registry, you can version-control your safety logic alongside your agent logic.

* **Structure:**
    * `/registry/tools/`: Python-based skills (e.g., `web_search.py`, `shell_executor.py`).
    * `/registry/agents/`: Definitions of Agno agents (instructions, model choice).
    * `/registry/workflows/`: Complex multi-agent sequences.
    * **`/registry/guardrails/`**: Custom validation logic (e.g., `pii_masking.py`, `code_safety.py`).
* **Implementation:** Create a `RegistryLoader` class that scans these directories and returns ready-to-use Agno objects.
* **The Guardrail Wrapper:** Ensure your guardrails follow a standard interface so the Orchestrator can "attach" them to any agent or workflow dynamically based on the request's risk level.



---

## Phase 2: The Orchestrator & ChromaDB
This layer is the "Dispatcher." It doesn't do the work; it decides *who* does the work and *how* they should behave.

* **ChromaDB Integration:** * On startup, the system generates embeddings for the descriptions of every item in your `/registry/`.
    * These embeddings (vectors) are stored in a local **ChromaDB** collection.
* **The Semantic Router:** * User sends a prompt (e.g., "Analyze this CSV for trends").
    * The Orchestrator queries ChromaDB: `collection.query(query_texts=[prompt], n_results=1)`.
    * It retrieves the `DataAnalysisWorkflow` and the `FileSafetyGuardrail`.
* **Job Manifest Construction:** The Orchestrator produces a JSON "Plan" that includes the workflow ID, the specific guardrail IDs to apply, and the initial user parameters.

---

## Phase 3: The Docker Sandbox (Local)
Since we are keeping it local, we use the Docker socket to spin up an environment that is "clean" for every run.

* **Execution Flow:**
    1.  **Trigger:** The Orchestrator sends the Job Manifest to a local `Runner`.
    2.  **Spin-up:** The Runner starts a Docker container using a pre-built Agno image.
    3.  **Injection:** The container mounts the specific files needed from the `/registry/` as read-only volumes.
    4.  **Enforcement:** The Agno workflow starts inside the container, with the **Registry Guardrails** wrapped around the agent's input/output streams.
* **Security:** This ensures that even if the agent attempts a "Skill" that involves file system access, it only happens inside the isolated container volume.

---

## Phase 4: Local Observability Bridge
You need to see what's happening inside that black-box container in real-time.

* **The Event Stream:** Configure your Agno fork to pipe all `logger` and `telemetry` events to a local SQLite database that is shared between the Host and the Container.
* **Live Feedback:** Your Web UI polls this shared database to show the "Thinking" process, tool calls, and guardrail "Pass/Fail" statuses.
* **Artifact Sync:** When a workflow finishes, it moves output files to a shared `/outputs/` folder. The UI then picks these up to display as charts, tables, or downloads.

---

## Phase 5: The "Command Center" Web UI
A simple interface to interact with your local agent factory.

* **Registry Browser:** A view to see all available Agents, Skills, and Guardrails currently in your folders.
* **The Sandbox Log:** A real-time terminal view showing the container's standard output.
* **Artifact Gallery:** A side panel that populates with files as they are generated by the containerized Agno agents.

---

## Phase 6: Production Optimizations
Enhancements to improve the efficiency and robustness of the system once the core functionality is established.

* **Smart Embedding Management:** Instead of regenerating the vector database embeddings on every startup:
    * Check if the ChromaDB collection is empty before doing a bulk index.
    * Implement a file watcher (e.g., `watchdog`) or an admin endpoint to only update the embeddings for a specific component when its file is added, modified, or deleted from the `/registry/` directory.
